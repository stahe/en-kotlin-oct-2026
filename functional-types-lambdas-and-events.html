    7. Functional Types, Lambdas, and Events

    In many programs, we need to pass not data but behavior to a function: the sorting criterion, the filtering condition, or the action to be performed when something happens. Kotlin addresses this need by treating functions as values just like any other: a function has a type—the functional type, denoted, for example, as [(Int, Int) -> Int]; it can be stored in a variable, passed as a parameter, returned as the result of another function, and executed whenever desired. A function that takes or returns a function is called a higher-order function.

    Java, as a reminder, does not have functional types: it relies on functional interfaces—interfaces with a single abstract method ([Runnable], [Comparator], [Function<T, R>]…), and it wasn’t until Java 8 (2014) that it allowed them to be implemented using lambda expressions and method references. Kotlin has supported lambdas since its very first version, and it can also work with Java’s functional interfaces, since it directly uses Java libraries. We’ve already used lambdas extensively without going into detail, in the collection operations covered in Chapter 5: in [personnes.filter { it.age >= 18 }], we pass a lambda to the function [filter]. This chapter explains what lies behind this syntax. It concludes with events, which Kotlin—like Java—handles using “listeners”: functions, most often lambdas, that register with an emitter to be notified of what is happening there. Graphical user interfaces (Swing, JavaFX, Compose) and web frameworks alike rely on this mechanism: a button click or the arrival of a HTTP request is signaled to registered listeners. This course does not cover graphical user interfaces; all examples are console programs.

    The programs in this chapter are organized in the Gradle project [07-lambdas], with one package per program: [src/main/kotlin/lambdas01/Lambdas01.kt], [src/main/kotlin/lambdas02/Lambdas02.kt]… They are run using [gradlew -q run -Pmain=lambdas01.Lambdas01Kt] or by clicking the green triangle in IntelliJ or IDEA. The project requires no libraries other than the standard Kotlin library: functional types, lambdas, and scope functions are included, and the interfaces in the [java.util.function] package are the same as those in JDK.

    7.1. Functional types and predefined functional interfaces

    7.1.1. The Concept of a Functional Type

    A functional type describes a model (also called a signature or a form) of a function: the types of its parameters, enclosed in parentheses, followed by an arrow, and then the type of its return value. A variable of a functional type can refer to any function of this form and execute it. Here are a few examples:

    • [() -> Unit]: a function with no parameters that returns no useful result ([Unit] plays the role of Java’s [void]);
    • [() -> String]: a function with no parameters that returns a string;
    • [(Int) -> Boolean]: a function that takes an integer and returns a boolean, in other words, a predicate;
    • [(Int, Int) -> Int]: a function that takes two integers and returns an integer;
    • [(String) -> (Int) -> Int]: a function that takes a string and returns… a function of type [(Int) -> Int] (the arrow is read from right to left);
    • [(() -> Unit)?]: a function that may be absent; the parentheses are necessary because [() -> Unit?] would otherwise denote a function returning a [Unit?]. Here we see the safety property with respect to [null] from Chapter 3: such a function is denoted by [f?.invoke()];
    • [String.(Int) -> String]: a function with a receiver; it is applied to a string—which its code denotes as [this]—as an extension function (Chapter 4). It can be called as an extension (["ab".f(3)]) or as an ordinary function whose receiver is the first parameter ([f("ab", 3)]).

    Parameters can be named to document the type: [(n1: Int, n2: Int) -> Int] is the same type as [(Int, Int) -> Int].

    There are three ways to obtain a value of a function type:

    • write a function call to an existing function that has the correct form: [val tache: () -> Unit = ::afficher];
    • Write a lambda expression: [val tache: () -> Unit = { println("tâche") }];
    • write an anonymous function: [val tache = fun() { println("tâche") }], or an object of a class that implements the functional type (a functional type is an interface, as we’ll see). These two notations are less common.

    The function is then executed like an ordinary function: [tache()]. This is a shorthand notation for calling the method [invoke] of the function object: [tache.invoke()]. This is the first noticeable difference from Java, where you must call the interface’s method by name ([run], [apply], [test]…); Kotlin behaves here like C#, where a delegate is called like a method.

    7.1.2. Kotlin Functional Types and java.util.function Interfaces

    Before Java 8, each Java library defined its own single-method interfaces ([Runnable], [Comparator], [ActionListener]…). Java 8 introduced the [java.util.function] package, which provides 43 generic functional interfaces. Kotlin does not need them: a functional type is written directly. However, these interfaces can still be used from Kotlin, and you’ll encounter them whenever you call a Java library. The following table maps the main Java interfaces to Kotlin’s functional types:

    In Kotlin, there is no practical limit to the number of parameters a function type can have: [(Int, Int, Int) -> Int] is written just as simply as the others, whereas in Java, since there is no predefined interface with three parameters, you have to define your own.

    How does the Java Virtual Machine, which only recognizes classes and interfaces, represent a functional type? Through generic interfaces from the Kotlin library: [kotlin.jvm.functions.Function0<R>], [Function1<P1, R>], [Function2<P1, P2, R>]… all the way up to [Function22], followed by an interface [FunctionN] beyond that. Each has a single method, [invoke]: [(Int, Int) -> Int] is compiled into [Function2<Integer, Integer, Integer>], whose method is [operator fun invoke(p1: Int, p2: Int): Int]. It is the modifier [operator] of [invoke] (see operator overloading in Chapter 4) that allows the notation [f(2, 3)]. A functional type is therefore, for JVM, a functional interface like those in Java. Since Java generics apply only to object types, [Int] values passed to a [(Int, Int) -> Int] are converted to [Integer] and vice versa (boxing and unboxing). Java avoids these conversions with its specialized interfaces ([IntBinaryOperator]…); Kotlin avoids them in a different way, using the [inline] functions, which we’ll discuss later.

fun main() {
     // 1 - () -> Unit: no parameters, no return value
    val tache: () -> Unit = ::afficher
     // Execution: the function is called like a regular function
    tache()
     // which is a shorthand notation for calling its `invoke` method
    tache.invoke()

     // 2 - (Int, Int) -> Int: two parameters, one result
    val operation: (Int, Int) -> Int = ::ajouter
    println("operation(2, 3)=${operation(2, 3)}")
     // () -> String: no parameters, one result
    val saluer: () -> String = ::saluer
    println("saluer()=${saluer()}")

     // 3 - (String) -> Unit: one parameter, no return value
    val ecrire: (String) -> Unit = ::println
    ecrire("(String) -> Unit a exécuté println")

     // 4 - (Int) -> Boolean: one predicate
    val estPair: (Int) -> Boolean = ::estPair
    println("estPair(8)=${estPair(8)}")
    val nombres = mutableListOf(3, 8, 1, 6, 5, 4)
     // removeAll from the Kotlin library expects an (Int) -> Boolean
    val modifiee = nombres.removeAll(estPair)
    println("nombres pairs retirés : $modifiee, reste : $nombres")

     // 5 - a `Comparator<T>` (Java interface) constructed from a function (conversion SAM)
    val noms = mutableListOf("Paul", "Mélanie", "Jo", "Sébastien")
    noms.sortWith(Comparator(::comparerLongueurs))
    println("triés par longueur : $noms")

     // 6 - the interfaces from java.util.function remain usable
    val fournisseur: Supplier<String> = Supplier(::saluer)
    val multiplier = IntBinaryOperator(::multiplier)
    val predicat = Predicate<Int> { it > 4 }
    println("fournisseur.get()=${fournisseur.get()}")
    println("multiplier.applyAsInt(2, 3)=${multiplier.applyAsInt(2, 3)}")
     // removeIf is a Java method (Collection): it expects a Predicate
    val valeurs = mutableListOf(10, 3, 8, 7, 2, 1)
    valeurs.removeIf(predicat)
     // A Kotlin function is automatically converted to a Predicate (conversion SAM)
    valeurs.removeIf(estPair)
    valeurs.removeIf { it == 1 }
    println("après removeIf : $valeurs")

     // 7 - a nullable functional type: the function may be absent
    executer(null)
    executer(tache)

     // 8 - a functional type with a receiver: String.(Int) -> String
    val repeter: String.(Int) -> String = String::repeat
    println("\"ab\".repeter(3)=${"ab".repeter(3)}, repeter(\"cd\", 2)=${repeter("cd", 2)}")

     // 9 - a function is an object, an instance of a class that implements an interface
    println("classe : ${operation::class.java.name}")
    println("interfaces : ${operation::class.java.interfaces.contentToString()}")
    val somme: (Int, Int) -> Int = { n1, n2 -> n1 + n2 }
    println("classe de la lambda : ${somme::class.java.name}")
    println("interfaces : ${somme::class.java.interfaces.contentToString()}")
}

     // safe call: nothing is executed if the callback is null
    rappel?.invoke()
    println("rappel ${if (rappel == null) "absent" else "présent"}")
}

    7.2. Defining Your Own Functional Types

    Functional types are often sufficient, but you may want to give a name to a function model. Kotlin offers two tools for this purpose, which are very different in nature.

    The first is a type alias, declared using the keyword [typealias]:

    • [typealias OperationBinaire = (n1: Int, n2: Int) -> Int]

    An alias does not create a new type: [OperationBinaire] is another name for [(Int, Int) -> Int], and the two notations are interchangeable. The alias makes the code more readable when the functional type is long or appears frequently.

    The second is the functional interface, declared by [fun interface]:

    • [fun interface Operation { fun calculer(n1: Int, n2: Int): Int }]

    This is the exact equivalent of a functional Java interface: an interface with only one abstract method (also known as a SAM, or “Single Abstract Method” interface). It may also have methods with bodies and non-abstract properties; these do not count. The keyword [fun] preceding [interface] serves the same purpose as the Java annotation [@FunctionalInterface], with one important difference: it is not optional. It is this keyword that enables the SAM conversion—that is, the creation of a [Operation] object from a lambda or a function reference: [Operation { n1, n2 -> n1 + n2 }]. Without the keyword [fun], a Kotlin interface—even one reduced to a single method—can only be implemented by a class or an anonymous object ([object : Operation { … }]).

    Compared to the type [(Int, Int) -> Int], the type [Operation] is a truly new type, distinct from all others: it has a name that describes its purpose, its method has a descriptive name ([calculer] rather than [invoke]), it can have additional methods, and it can be implemented by a named class. Conversely, it is executed by its method name ([op.calculer(2, 3)]), not by [op(2, 3)].

    A variable named [op] of type [Operation], like a variable of type [(Int, Int) -> Int], references only one function at a time. Unlike C#, which offers “multicast delegates,” neither Java nor Kotlin provides a way to store multiple functions in a single variable and execute them all with a single call: when needed, we store the functions in a list and execute them one by one. This is exactly what we’ll do with event listeners.

import java.util.function.IntBinaryOperator

// Defining your own functional types: `fun`, `interface`, and `typealias`

fun main() {
     // A variable of type `Operation` receives the `increase` function from the companion object
    var op = Operation(Calculs::augmenter)
     // The operation is executed
    var n = op.calculer(4, 7)
    println("n=$n")

     // Creating an object c1 of type Calculations
    val c1 = Calculs()
     // The `ajouter` method of the `c1` object is stored in `op`
    op = Operation(c1::ajouter)
    n = op.calculer(2, 3)
    println("n=$n")
     // then the `subtract` method of `c1`
    op = Operation(c1::soustraire)
    n = op.calculer(2, 3)
    println("n=$n")

     // A variable references only one function: to execute multiple functions, use a list
    val operations = listOf(
        Operation(c1::ajouter),
        Operation(c1::soustraire),
        Operation { n1, n2 -> n1 * n2 },
    )
    for (operation in operations) {
        println("-> ${operation.calculer(10, 4)}")
    }

     // A method of the interface creates a new operation
    val sommeAuCarre = Operation(c1::ajouter).puis { x -> x * x }
    println("sommeAuCarre.calculer(1, 2)=${sommeAuCarre.calculer(1, 2)}")

     // Operation and IntBinaryOperator have the same form but are two different types
    val autre = IntBinaryOperator(op::calculer)
    println("autre.applyAsInt(5, 1)=${autre.applyAsInt(5, 1)}")

     // a generic functional interface
    val longueur = Transformation(String::length)
    val etoiles = Transformation("*"::repeat)
    println("longueur(\"Bonjour\")=${longueur.transformer("Bonjour")}")
    println("etoiles(5)=${etoiles.transformer(5)}")

     // a type alias: simply another name for (Int, Int) -> Int
    val f: OperationBinaire = { n1, n2 -> n1 - n2 }
     // OperationBinaire and (Int, Int) -> Int are the same type
    val g: (Int, Int) -> Int = f
     // but `Operation` is a different type: a conversion is required
    val op2 = Operation(g)
    println("f(5, 1)=${f(5, 1)}, g(5, 1)=${g(5, 1)}, op2.calculer(5, 1)=${op2.calculer(5, 1)}")
}

// Definition of a functional interface: a single abstract method
// that takes two integers as parameters and returns an integer
fun interface Operation {
    fun calculer(n1: Int, n2: Int): Int

     // A method with a body does not count: the interface remains functional
    fun puis(suite: (Int) -> Int): Operation = Operation { n1, n2 -> suite(calculer(n1, n2)) }
}

// A generic functional interface: T -> R
fun interface Transformation<T, R> {
    fun transformer(valeur: T): R
}

// a type alias: no new type is created
typealias OperationBinaire = (n1: Int, n2: Int) -> Int

// a class whose methods have the form of the Operation interface
class Calculs {
     // two instance methods
    fun ajouter(n1: Int, n2: Int): Int {
        println("ajouter($n1,$n2)")
        return n1 + n2
    }

    fun soustraire(n1: Int, n2: Int): Int {
        println("soustraire($n1,$n2)")
        return n1 - n2
    }

     // a companion object method: the equivalent of a static method
    companion object {
        fun augmenter(n1: Int, n2: Int): Int {
            println("augmenter($n1,$n2)")
            return n1 + 2 * n2
        }
    }
}

    A lambda is not quite a shorthand for an anonymous object. In this course, we will use lambdas whenever possible.

We will return to this topic in Chapters 8 and 9. The functions [inline], presented later, also avoid the creation of [Ref] objects when the lambda is copied into the calling code.

    7.4. Inline Functions and Scope Functions

    7.4.1. Inline functions

    A lambda is an object. Passing a lambda to a higher-order function therefore incurs a cost: the creation of the object (except for a lambda that captures nothing, which the virtual machine can reuse), the call to its [invoke] method, the [Int] ↔ [Integer] conversions imposed by the generic interfaces [Function1], [Function2]…, and the [Ref] objects of the captured variables. For a function like [filter], which is called on every element of collections that can sometimes be very large, this cost matters. Kotlin eliminates this with the [inline] modifier: when a function is declared [inline fun], the compiler does not generate a call to that function; instead, it copies its code to every location where it is called, and it also copies the code of the lambdas passed to it. As a result, there are no longer any lambda objects, no [invoke] calls, and no conversions. The standard library functions that accept lambdas ([forEach], [filter], [map], [fold], [let], [apply], [repeat], [use], [synchronized]…) are almost all [inline]. Java has no equivalent: it relies on the virtual machine’s on-the-fly compiler to produce a result comparable to runtime execution.

    The insertion of the code has a second, more noticeable consequence: since the lambda’s code is copied into the calling function, an unlabeled [return] instruction can exit the calling function from there. This is the non-local return encountered with *[forEach] in *[Lambdas03.kt]. Two modifiers complement *[inline]*:

    • [noinline], applied to a function parameter of a [inline] function, specifies that the corresponding lambda should not be copied, but passed as a regular object. This is necessary when the function wants to retain the lambda (store it in a list, return it as a result, etc.): copied code cannot be stored in a list;
    • [crossinline] requires that the lambda be copied, but prohibits non-local returns. This is necessary when the function [inline] does not execute the lambda itself, but executes it in another context—for example, within a [Runnable] object that it creates: When [Runnable] executes, the calling function may have long since finished, and a [return] would no longer be able to exit it.

The first is specific to Kotlin: for a functional parameter, is a functional type required, or is a [fun interface] sufficient?

    • The functional type is the default choice. It requires no declaration, is called like a function, directly accepts lambdas and references, and benefits from [inline] functions. A [typealias] gives it a name when it is long;
    • the “fun” interface is justified when you want a truly distinct type (one that cannot be confused with another function of the same form), a method with a descriptive name, additional methods with a body, or a API also intended for Java callers: for Java, a [fun interface] is an ordinary functional interface, usable with its lambdas, whereas a Kotlin functional type appears to it as a [Function2<Integer, Integer, Integer>] whose [invoke] method must return an object ([Unit] for a “returnless” function).

    The second question is the same as in Java: should the interface have a single method, or multiple ones?

    • A function, functional type, or single-method interface is more flexible to use: any existing function with the correct form will work, and a lambda even allows you to write the function right where it’s called. There is no class to write. This flexibility explains why modern libraries (collections, the coroutines in Chapter 9, Spring) make extensive use of functional parameters;
    • an interface with multiple members regains the advantage as soon as the behavior to be implemented involves several interrelated operations ([calculer] and [nom] above), or when it requires its own state and identity.

    This is the case for the [IImpotDao] interface in the [dao] layer from Chapter 6: although it has only one member—the [val tranchesImpot: List<TrancheImpot>] property—its implementations have state (the chunks read, the file name), are created by the dependency injection container, and represent a clearly named role within the application. A [() -> List<TrancheImpot>] would technically have sufficed, but it would have been much less descriptive. We therefore reserve functional types for short, one-off behaviors (a criterion, a transformation, an action), and “business” interfaces for the application’s roles, regardless of the number of their members.

    7.6. Event Handling

    7.6.1. The Observer Pattern

    Functions passed as parameters are used to set up events. Like Java, Kotlin has no dedicated keyword for events (C# has its own keyword, [event]): it uses the conventions established by Java as early as version 1.1 for graphical components and JavaBeans, known as the “listener model.” A [C1] class that wants to signal a [Xxx] event proceeds as follows:

    • A [XxxEvent] class encapsulates information about the event, including the object that triggered the event, known as the source. In Java, the convention is for it to derive from [java.util.EventObject], which stores the source; in Kotlin, a regular class with read-only properties is sufficient, and that is what we will do;
    • A listener type defines the form of the function that will be called when the event occurs. In Java, this is an interface named [XxxListener]; in Kotlin, it is most often a simple functional type, [(XxxEvent) -> Unit], named by a [typealias]: a listener will be a lambda or a function reference;
    • the [C1] class manages a list of functions and provides two public methods for registering and unregistering with it: [addXxxListener(listener)] and [removeXxxListener(listener)];
    • When a [c1] instance of [C1] wants to signal the event, it creates a [XxxEvent] object and calls each of the registered listeners, passing this object to them. By convention, this notification is handled by a protected method [fireXxx(e: XxxEvent)] (“fire”), which a derived class can override to modify how the event is published;
    • If an object [c2] wants to be notified of the event [Xxx] from the object [c1], it subscribes using [c1.addXxxListener(...)]. It can unsubscribe via [c1.removeXxxListener(...)] when it no longer wishes to be notified. Since [c1] manages a list, different objects can subscribe to be notified of the same event.

    In this scenario, we have:

    • a class that signals (also called “publishes” or “emits”) an event;
    • objects that are notified of this event. They are said to subscribe to or register for the event: these are the listeners, or event handlers;
    • a type of listener that defines the form of the functions that will be notified of the event.

    This is the Observer design pattern: the emitter does not know its subscribers; it simply notifies them. This model offers the same protection as a dedicated keyword: the list of listeners is a private property of the emitter. From the outside, one can only subscribe or unsubscribe; one cannot clear the list, replace other listeners, or trigger the event in place of the emitter.

    7.6.3. Property Change Events

    The most common type of event occurs when an object’s property changes value: another object (a graphical user interface, a cache, a log) wants to be notified of this change. Kotlin and the Java library provide two complementary tools for this scenario:

    • Kotlin's delegated properties. A property declared as [var p: T by delegue] delegates the reading and writing of its value to another object, the delegate. The standard library provides several of these, such as [by lazy { … }], which calculates the property’s value on the first access. The object [kotlin.properties.Delegates] provides two delegates that accept a lambda: [Delegates.observable(valeurInitiale) { propriete, ancienne, nouvelle -> … }] executes the lambda after each write to the property; [Delegates.vetoable(valeurInitiale) { propriete, ancienne, nouvelle -> … }] executes it beforehand and accepts the new value only if the lambda returns [true]. The parameter [propriete] is a reference to the property ([KProperty]), whose name is obtained via [propriete.name];
    • the Java class [java.beans.PropertyChangeSupport], which manages the list of listeners for us. The listeners implement the functional interface [PropertyChangeListener], whose method [void propertyChange(PropertyChangeEvent evt)] receives an event containing the source, the property name, and its old and new values.

class Thermometre(nom: String) {
     // Listener management is delegated to an object PropertyChangeSupport
    private val changements = PropertyChangeSupport(this)

     // an observable property: after each write, the change is signaled
    private fun <T> observable(valeurInitiale: T): ReadWriteProperty<Any?, T> =
        Delegates.observable(valeurInitiale) { propriete, ancienne, nouvelle ->
            changements.firePropertyChange(propriete.name, ancienne, nouvelle)
        }

    var nom: String by observable(nom)
    var temperature: Double by observable(0.0)

     // a property that rejects values outside the range [5, 30]
    var consigne: Double by Delegates.vetoable(20.0) { _, _, nouvelle -> nouvelle in 5.0..30.0 }

     // registering and unregistering listeners
    fun addPropertyChangeListener(listener: PropertyChangeListener) {
        changements.addPropertyChangeListener(listener)
    }

    fun addPropertyChangeListener(propriete: String, listener: PropertyChangeListener) {
        changements.addPropertyChangeListener(propriete, listener)
    }

    fun removePropertyChangeListener(listener: PropertyChangeListener) {
        changements.removePropertyChangeListener(listener)
    }

    val nbEcouteurs: Int
        get() = changements.propertyChangeListeners.size

// filters a list using a predicate: the work performed by the filter function
inline fun <T> List<T>.filtrer(predicat: (T) -> Boolean): List<T> {
    val resultat = mutableListOf<T>()
    for (element in this) {
        if (predicat(element)) {
            resultat.add(element)
        }
    }
    return resultat
}

fun estImpair(n: Int) = n % 2 != 0

// an intermediate sequence operation that only lets through elements that satisfy the predicate
fun <T> Sequence<T>.garder(predicat: (T) -> Boolean): Sequence<T> = sequence {
    for (element in this@garder) {
        if (predicat(element)) yield(element)
    }
}

// an intermediate operation that transforms each element: the equivalent of `map`
fun <T, R> Sequence<T>.transformer(transformation: (T) -> R): Sequence<R> = sequence {
    for (element in this@transformer) {
        yield(transformation(element))
    }
}

    7.8. Expression Trees

    Some languages, such as C#, allow a lambda to be converted not into executable code, but into a data structure that describes it (an “expression tree”): a program can then parse the lambda [t => t.Limite > 20000] and translate it, for example, into a clause SQL [WHERE limite > 20000] executed by the database server.

    Kotlin, like Java, has no equivalent: a Kotlin lambda is always compiled into executable code; it can be called, but its internal workings cannot be examined. Several tools come close, however:

    • Property references: [Personne::age] is an object ([KProperty1<Personne, Int>]) that knows the property name ([Personne::age.name]) and its type. A library can use this to construct a query without writing a string: this is what Spring Data MongoDB does, for example, with its Kotlin extensions, which allow you to write a criterion such as [Personne::age gt 18];
    • Internal DSL (“Domain-Specific Languages”): thanks to lambdas with receivers, [infix] functions, and operator overloading, a Kotlin library can offer a syntax similar to SQL, which the program executes to construct a data structure describing the query. This is the principle behind the Exposed library, from JetBrains: [Tranches.selectAll().where { Tranches.limite greater 20000 }];
    • compiler plugins: the Kotlin compiler can be extended with plugins that transform the code. This is how kotlinx.serialization works, the [all-open] and [no-arg] plugins used with Spring and Hibernate, or the [power-assert] plugin, which analyzes an assertion’s expression to display its details in case of failure. However, these are development tools, not built-in features of the program.

    Hibernate, which we will cover in Chapter 11, offers the same solutions as in Java: a query language similar to SQL but expressed in terms of classes and properties, HQL (["from Tranche t where t.limite > 20000"]), and Jakarta Persistence’ API Criteria, which constructs the query through method calls ([cb.gt(t.get("limite"), 20000)]). In both cases, the query is data (a string or an object tree) that Hibernate translates into SQL, whereas a lambda passed to [filter] is executed within the Kotlin program.

    7.9. Conclusion

    Key takeaways from this chapter:

    • In Kotlin, functions are values: they have a functional type ([(Int, Int) -> Int], [() -> Unit], [(T) -> Boolean], [(() -> Unit)?], [T.() -> R]…), can be stored in variables, passed as parameters, returned as results, and called like ordinary functions. To the virtual machine, they are objects that implement the interfaces [Function0], [Function1]…;
    • the interfaces of [java.util.function] ([Function], [Supplier], [Consumer], [Predicate]…), along with [Runnable], [Callable], and [Comparator], remain usable: when a Java method expects a functional interface, Kotlin automatically converts a lambda or a reference to it (conversion SAM); elsewhere, the conversion is written explicitly: [Comparator { … }];
    • to name a function type, we have the alias [typealias] (simply an alias) and [fun interface] (a true new type, implementable via a lambda);
    • A function can be obtained via a lambda expression ([{ a, b -> a + b }], [{ it * it }]—written outside parentheses when it is the last parameter, and closed with [return@etiquette]), via an anonymous function, via an anonymous object, or via a reference ([::fonction], [objet::methode], [Classe::methode], [::Classe]). Two references to the same function of the same object are equal; two lambdas are never equal;
    • lambdas capture the variables surrounding them, including the [var], which they can modify (the compiler stores them in [Ref] objects); they then see the value of the variable at the time of their execution, which requires caution in loops and between threads;
    • Functions that return functions and extensions on functional types ([puis], [et], [ou]…) compose new functions; [compareBy], [thenBy], and [reversed] construct comparators;
    • the functions [inline] copy their code and that of the lambdas to the call site, without an object or conversion, and allow non-local returns; [noinline] and [crossinline] handle special cases. The scope functions [let], [run], [with], [apply], and [also] are the most common applications of this;
    • a functional type is chosen for short-term, one-off behavior; a [fun interface] for a distinct type; or a API that can be used from Java; a multi-member interface (or a “business” interface) for an application role;
    • an event is set up using the listener pattern: a [XxxEvent] class, a listener type (often a functional-type [typealias]), [addXxxListener] / [removeXxxListener], and a list of functions ([CopyOnWriteArrayList]) iterated over by a [fireXxx] method. The delegated properties [Delegates.observable] and [Delegates.vetoable] signal or filter changes to a property, and [PropertyChangeSupport] manages the list of listeners for them;
    • collection operations (immediate, [inline]) and sequence operations (lazy) are higher-order functions; Kotlin does not have expression trees, and Hibernate expresses its queries using HQL or the API Criteria.

    Lambdas will reappear in all subsequent chapters: a thread executes a lambda ([thread { … }]), and a [ExecutorService] executes a [Callable] (Chapter 8); a coroutine is launched by [launch { … }] or [async { … }] (Chapter 9), extension functions of [ResultSet] will receive, in the form of a lambda, the transformation of a line from the result into an object (Chapter 10), and Spring Boot web services process HTTP requests in methods that the framework calls as listeners (Chapter 13).
